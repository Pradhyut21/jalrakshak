# CampusEvac and Fraud Risk Manager: static reference review

Reviewed 1 October 2026 for SAANS preparation. This is planning research, not hackathon submission implementation. Repositories were shallow-cloned into a separate temporary directory and read; repository code, dependency installation, tests, deployments, and live application workflows were **not executed**. CampusEvac's committed screenshots were visually inspected. Existing README assertions of success or impact are not independent evidence of prizes, production readiness, or real-world outcomes. These findings describe the current pinned commits, not necessarily the versions judged at their respective events.

## CampusEvac: make the intervention visible

Its strongest transferable idea is **one shared situation viewed through two useful roles**. The evacuee experiences the problem; the warden observes evidence and communicates or intervenes. The committed [evacuee screenshot](https://github.com/AfreenInnovates/campus/blob/568a585021fae096799599bb3d3fbbb9f6b3e6f6/image7.png) and [warden screenshot](https://github.com/AfreenInnovates/campus/blob/568a585021fae096799599bb3d3fbbb9f6b3e6f6/image8.png) show objectives, location, air/health, evidence and the sequence Observe → Verify → Send route → Clear smoke. A viewer can understand the action loop visually. They are historical repository images, not screenshots captured from a running build during this review.

The [CDK stack](https://github.com/AfreenInnovates/campus/blob/568a585021fae096799599bb3d3fbbb9f6b3e6f6/infra/lib/campusevac-stack.ts) creates an AppSync Events API and DynamoDB table. The `/live` namespace broadcasts movement; `/game` persists meaningful events through a [publish handler](https://github.com/AfreenInnovates/campus/blob/568a585021fae096799599bb3d3fbbb9f6b3e6f6/infra/src/game-handler.js). This gives each AWS service a visible purpose while avoiding writes for every movement update.

Limits to learn from: no automated test suite or test command was found in the inspected tree/package scripts; public API-key authorization and client-authored events are demo-level trust assumptions. Claims about improved emergency behavior, uniqueness, and zero marginal cost need evidence beyond this repository. Do not copy its 3D engine for a school-air or water deadline product unless 3D is essential to the user's decision.

## Fraud Risk Manager: make each assertion inspectable

The [scorer](https://github.com/aaryanpawar16/fraud-risk-manager/blob/3937fae0085469e9e1613d07f2647903f9051dd8/backend/app/services/scorer.py) loads two separate model artifact directories; the return signal is not simply a renamed chargeback score. Its [Dashboard](https://github.com/aaryanpawar16/fraud-risk-manager/blob/3937fae0085469e9e1613d07f2647903f9051dd8/frontend/src/pages/Dashboard.tsx) exposes metrics, cost tradeoffs, confusion matrix, drift and baseline comparison. The [policy simulator](https://github.com/aaryanpawar16/fraud-risk-manager/blob/3937fae0085469e9e1613d07f2647903f9051dd8/frontend/src/components/risk/PolicySimulator.tsx) connects a threshold choice to projected monthly cost and explicitly labels savings as projected.

The [saved comparison](https://github.com/aaryanpawar16/fraud-risk-manager/blob/3937fae0085469e9e1613d07f2647903f9051dd8/backend/ml/reports/baseline_comparison.json) reports logistic regression ROC-AUC about **0.78049**, ahead of XGBoost **0.7668**, on a 4,000-row holdout. [Comparison tests](https://github.com/aaryanpawar16/fraud-risk-manager/blob/3937fae0085469e9e1613d07f2647903f9051dd8/backend/ml/tests/test_baseline_comparison.py) deliberately do not demand that the more complex model win. This is a good reporting habit, not validation of performance on real merchant data.

Important boundaries and defects:

- **Synthetic labels:** [generator](https://github.com/aaryanpawar16/fraud-risk-manager/blob/3937fae0085469e9e1613d07f2647903f9051dd8/backend/ml/generate_synthetic_data.py) synthesizes both `chargeback` and `returned` outcomes from logistic probabilities. The README's phrase “real return outcomes” should therefore not be repeated as a real-world data claim.
- **Chronological split is insufficient by itself:** the same generator assigns random event timestamps, updates customer history in generation order, and only afterward sorts rows. Point-in-time history may therefore contain future outcomes. In the committed raw CSV, customer `cust_ff1d4796fe`'s earliest row, `ORD-0015036` at `2025-01-01T00:56:00`, already has six previous orders, five previous returns and two previous chargebacks. This is a static source/data finding; do not describe its feature pipeline as proven leakage-free solely because split timestamps are ordered.
- **Documentation drift:** [human report](https://github.com/aaryanpawar16/fraud-risk-manager/blob/3937fae0085469e9e1613d07f2647903f9051dd8/docs/metrics_report.md) says AP 0.442 and cost ₹955,900; [machine report](https://github.com/aaryanpawar16/fraud-risk-manager/blob/3937fae0085469e9e1613d07f2647903f9051dd8/backend/ml/reports/metrics_report.json) has AP 0.4526 and cost ₹974,400. Generate prose/tables from one frozen evaluation artifact.
- **Notification failure semantics:** [alerting implementation](https://github.com/aaryanpawar16/fraud-risk-manager/blob/3937fae0085469e9e1613d07f2647903f9051dd8/backend/app/services/alerting.py) returns `None` when webhook delivery fails but still records the alert and returns `True`. A subsequent call is deduplicated. Copy the integration-testing habit, not this success/retry behavior.
- **Evidence versus asserted evidence:** [PDF builder](https://github.com/aaryanpawar16/fraud-risk-manager/blob/3937fae0085469e9e1613d07f2647903f9051dd8/backend/app/services/evidence_builder.py) creates real PDF files from repository records, but parts of the dispute narrative are templated assertions. Downloadable output is not independent delivery proof or verification that manual review happened.

The [webhook tests](https://github.com/aaryanpawar16/fraud-risk-manager/blob/3937fae0085469e9e1613d07f2647903f9051dd8/backend/tests/test_alerting.py) use a real local HTTP receiver to inspect method, content type, payload and deduplication. [CI](https://github.com/aaryanpawar16/fraud-risk-manager/blob/3937fae0085469e9e1613d07f2647903f9051dd8/.github/workflows/tests.yml) defines ML/backend pytest runs and a frontend build. Test definitions and CI configuration were reviewed; pass counts and current CI status were not verified. The README acknowledges unauthenticated API, no frontend automated tests, and single-instance SQLite limits.

## Transfer to either SAANS direction

1. Make a real decision visible: **reading → risk → action with deadline → explicit approval → delivery status → fresh evidence → verification**. For water, animate tank reserve and supply timing. For school air, compare feasible schedule/space choices with data age, assumptions and decision rationale.
2. Borrow CampusEvac's guided scenario and explicit state transitions. A labelled simulation should reveal the problem and the consequence of intervention; a complex visual engine is optional.
3. Borrow Fraud Risk Manager's simple baseline, fixed evaluation artifact, independent arithmetic checks and local integration receiver. Evaluate false alarms, missed events and warning lead time, not just a flattering model metric.
4. Generate histories in chronological order. Construct all historical features using information available at that timestamp. Keep calibration/threshold selection separate from final holdout evaluation.
5. Keep `SIMULATED`, `PROJECTED`, `OBSERVED` and `VERIFIED` distinct in both API and UI. Notification accepted does not mean delivered, acted on or environmentally safe.
6. An assistant may explain tool-returned state and run supported what-if tools. Deterministic domain logic should own operational values, constraints and verification. Copy the evidence discipline and visual causal story; do not copy all pages/features.
